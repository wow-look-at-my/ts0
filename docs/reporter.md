# Output: GitHub Actions annotations + ANSI coloring

`src/reporter.ts` is the one place ts0 decides how to show a diagnostic. No command duplicates it. It backs three independent things:

1. **`::error::`/`::warning::` GitHub Actions annotations.** `annotate()` does nothing unless `GITHUB_ACTIONS=true` (`isGithubActions()`). A local terminal prints the workflow command syntax as literal `::error::...` noise. `formatAnnotation` applies GitHub's escaping rules to the message (`%`, CR and LF) and to property values (those plus `:` and `,`).
2. **Color support detection.** `colorEnabled()` forces color ON under GitHub Actions, although its stdout is a pipe and not a TTY. The Actions log viewer renders ANSI the same as a real terminal, so a bare `stream.isTTY` check leaves every CI run uncolored. Outside Actions it follows the stream's own TTY-ness. `NO_COLOR` and `FORCE_COLOR`, the usual community env vars, take precedence over both.
3. **Recoloring known output shapes**, through `colors()` (raw ANSI wrappers) and two higher-level functions built on it:
   - `colorizeErrorBlock(text, fallbackSeverity)` takes a block of ts0's own error or warning text: a `BuildResult.errors`/`.warnings` entry, or `runTypecheck()`'s `.output`. It parses each line against the tsc/ts0 diagnostic shape `file(line,col): error TSxxxx: message`. `formatDiagnostic` and `formatEsbuildDiagnostic` produce that same shape for esbuild's own messages, so every target reports it: default, js and HTML alike. A line that matches gets its location dimmed and its `error`/`warning` marker brightened, in that line's own severity color. It also becomes a GitHub annotation with the parsed file, line and column. Any other non-blank line is a header like "Build failed:", or a message with no location. Such a line is colored solid in `fallbackSeverity`, because it holds nothing more specific to highlight.
   - `colorizeTestLine(line)` takes one line of `node --test`'s TAP output. On a pass or fail line it colors only the `ok`/`not ok` token, because hundreds of passing tests drown out anything that needs attention. A failure also becomes a GitHub annotation, since a TAP line carries no file or line to point at instead. A nonzero `# fail N` summary is colored solid red. It is the one line allowed to be whole-line red for something other than a single diagnostic.
   - `pipeColorized(readable, colorizeLine, out?)` streams a spawned child's output through one of the above, line by line, as it arrives. `test.ts` uses it because `stdio: "inherit"`, the previous behavior, hands the child's fd straight to the terminal. That bypasses ts0, and therefore all recoloring.

## Why esbuild's own logging is off

`esbuild-base.ts` sets `logLevel: "silent"` in `baseEsbuildOptions()`. Without it, esbuild's Node API returns each error and warning in `result.errors`/`.warnings` AND prints its own colorized copy to the terminal. This was verified directly against the installed esbuild version. Two uncoordinated reports of one diagnostic are worse than one report. ts0's own reporting is the single source of truth. It annotates, and it formats the same as every other target. `build-html.ts`'s three inline esbuild calls already set this per call. The shared option covers the other two targets, `build.ts`'s default target and `build-js.ts`.

## Adding a new error/warning surface

Format the message as `formatDiagnostic(file, line, col, severity, message, code?)` whenever you have a real file and line to report. Reuse `formatEsbuildDiagnostic` instead if you already hold an `esbuild.Message`. Then pass the resulting text through `colorizeErrorBlock`, or through `colorizeTestLine` for TAP-shaped output, at the point where the console prints it. Never colorize inside `runTypecheck()`, `buildSelf()` or their peers. The raw text must stay available uncolored for anything that parses or asserts on it: the unit tests, the `.dats` suites, and a future caller.
