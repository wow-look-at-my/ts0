# Prebuilt ts0.cjs (buildhost packaging)

`scripts/build-prebuilt.ts` packages ts0 for buildhost as ONE platform-neutral CommonJS file plus five small platform-native esbuild binaries. CI publishes them to buildhost on every branch push. Consumers run `node ts0.cjs <cmd>`, or `curl ... | node - <cmd>`, on stock Node >= 22 with no npm. Node is the deliberate prerequisite. ts0 is a Node tool, and hosting a duplicate Node runtime per platform was rejected as waste.

How the pieces fit:

- **The bundle** (`src/prebuilt/main.ts` -> `ts0.cjs`): the CLI, the esbuild JS API, and the ENTIRE TypeScript compiler (pure JS) in one file. Three things are embedded as strings through the generated `ts0-prebuilt-assets` virtual module: the compiler API (`lib/typescript.js`), every `lib/lib.*.d.ts` standard library, and the whole `@types/node` package. An esbuild plugin injects that module at package time. `src/prebuilt/prebuilt-assets.d.ts` is the ambient declaration that keeps the repo type-check happy without it. ~14 MiB total, ~2 MiB gzipped on the wire.
- **`@types/node` ships embedded too**, so a Node-target project type-checks with no `@types/node` install of its own. `commands/build.ts`'s `generatedCompilerOptions` sets `typeRoots` to two directories: the extracted `node_modules/@types`, and the consumer's own. `nodeTypeRootsDir` resolves the first, with the same `createRequire(import.meta.url)` trick `runTsc` uses for `typescript`. An explicit install therefore still resolves. It is just never required. `@types/node` is a regular `dependencies` entry (not `devDependencies`) precisely because every consumption path, including a plain `npm install`, needs it resolvable from ts0's own installed tree.
- **So do the packages `@types/node` imports from.** `embedTypeDependencies` in `scripts/build-prebuilt.ts` walks that closure rather than listing it. A dependency added on a version bump therefore comes along, and one that cannot be resolved fails the packaging. Today the closure is `undici-types`. That is where `fetch` returns its `Response`. Embedding `@types/node` alone left a `Response` with no members. `(await fetch(url)).ok` then failed with "Property 'ok' does not exist on type 'Response'". The project's only fault was to trust the types ts0 supplies. The compiler reports the members rather than the missing package. An unresolved type import degrades to a shapeless type instead of an error. That is why the guard lives in the packaging, and why `scripts/prebuilt-smoke.sh` builds a program that calls `fetch`. From source there is nothing to catch: `undici-types` sits beside `@types/node` in ts0's own `node_modules`.
- **The compiler is embedded ONCE.** The npm package ships it twice. `lib/typescript.js` is the API. `lib/_tsc.js` is the same compiler rebuilt as a CLI, reached through `bin/tsc` -> `lib/tsc.js`. Both capabilities are needed: the gate spawns the CLI, and the explicit-`any` pass requires the API in-process. Embedding both adds ~9 MiB of duplicated compiler, so only the API ships. `scripts/build-prebuilt.ts` GENERATES `bin/tsc` (`TSC_DRIVER`) instead. The driver does what `_tsc.js` does at its tail: enable the compile cache, call `sys.setBlocking()` so a piped diagnostic dump cannot truncate, then call `executeCommandLine(sys, noop, sys.args)`. The driver was verified identical to the stock CLI on diagnostics text, exit codes and declaration-emit bytes. `runTsc` still spawns `node <bin/tsc> --project ...` unchanged, so the gate behaves exactly as it does on the npm path. `executeCommandLine` is a runtime export absent from `typescript.d.ts`. The packaging script asserts it exists, and the boot sanity runs one real failing build and one passing build through the driver. A TypeScript upgrade that moves it therefore breaks packaging rather than a consumer's first run.
- **Format is CommonJS, extension is .cjs, and both are load-bearing.** `node -` executes stdin as CJS with no flags, which is what keeps the pipe form (`curl ... | node - build`) flagless. A `.js` file also parses as ESM inside any consumer package that declares `"type": "module"`, this repo included. Do not rename the artifact to `.js` or switch the bundle to ESM without solving both.
- **Stdin-runnable invariant: nothing may depend on the bundle's own path.** Under `node -`, `__filename` is `[stdin]` and there is no `import.meta.url`. The packaging `define`s `import.meta.url` to `globalThis.__ts0PrebuiltImportMetaUrl`, and `runtime.ts` points that at `<cache>/<build-id>/dist/ts0`. So build.ts's `createRequire(...).resolve("typescript/bin/tsc")` finds the EXTRACTED compiler under `<cache>/node_modules/typescript`, and build-html.ts's `../src/runtime/fetch-interceptor.js` candidate finds the extracted template. Neither needs a source change. If you add a new `__filename`/`__dirname`/`import.meta.url` use to shared code, it must resolve via that anchor (or the cache), never via the bundle's location. (The bundled esbuild lib references `__filename` only on error paths that `ESBUILD_BINARY_PATH` short-circuits.)
- **Extraction** (`src/prebuilt/runtime.ts`): the first run writes the embedded files to `$TS0_CACHE_DIR`, or to `~/.cache/ts0/<build-id>/`. The write is an atomic temp-and-rename, and a concurrent racer uses the winner's tree. The build id is a hash of the final bundle plus the dependency versions, substituted into a placeholder after bundling. Any change therefore extracts fresh, and two upgrades never collide. tsc then runs exactly as in the npm build, as `node <extracted tsc> --project ...`. `node` is on PATH by prerequisite, so `ts0 run` and `ts0 test` need no change at all.
- **The one native piece: esbuild.** `ensureEsbuildBinary` fetches the platform's native binary (~11 MB) from `https://dl.pazer.build/ts0/esbuild-<version>?os=..&arch=..` into the cache, atomically and once. It exports `ESBUILD_BINARY_PATH` BEFORE it imports the CLI, and therefore before the bundled esbuild module, which snapshots that env var at load time. Keep that ordering. An `ESBUILD_BINARY_PATH` that is already set and exists is respected as a user override. `TS0_ESBUILD_URL` overrides the fetch URL, for a mirror or a test. A fetch failure names the URL and the destination. It is never a silent fallback. The natives come from the npm registry tarballs, verified against the package-lock sha512, so they are byte-identical to what npm installs. There is no esbuild-wasm fallback. That is deliberate, because it is not worth the weight.
- **npm-path invariant**: the prebuilt machinery lives entirely in `src/prebuilt/` + the packaging script. It made two changes to shared source: quoting in `runTsc`'s exec string, for a spaced path, and `nodeTypeRootsDir`'s `createRequire(import.meta.url).resolve(...)` in `build.ts`. Both resolve relative to wherever the running code actually lives. They therefore behave identically on the npm and git-install path, which is ts0's own `node_modules`, and on the prebuilt path, which is the extraction cache. Neither carries a prebuilt-specific branch. The npm/git-install path must never notice the prebuilt exists.
- **What must stay in sync when deps bump.** First, the typescript embed list in `embeddedFiles`. `lib/typescript.js` plus `lib/lib.*.d.ts` is a TypeScript-5.x layout, and the generated `bin/tsc` driver depends on the `executeCommandLine` runtime export. The script throws at package time if either moves. Second, the whole `@types/node` package. The script walks it recursively, so a version bump that adds or removes a file needs no list edit. Third, the esbuild version. The script reads it from the lockfile and bakes it into both the native-fetch URL and the buildhost project name, `ts0/esbuild-<version>`. An esbuild bump therefore publishes a new natives project on the next push.
- **CI/publish** (`.github/workflows/ci.yml`). The `prebuilt` job builds everything and runs `scripts/prebuilt-smoke.sh`. That is a bare-node smoke: `env -i`, PATH holds ONLY node, and it asserts npm and npx are unreachable. It exercises the real fetch path against a local HTTP server, the fetch-failure message, the PIPE form (`cat ts0.cjs | node - build`), the init flow, and the type-error gate. It also exercises the explicit-`any` ban, the pass that requires the extracted `lib/typescript.js` in-process, in the pipe form too. Then the extracted tree's shape: the API plus the generated `bin/tsc`, and NO `_tsc.js`, which is the no-duplicated-compiler assertion. Last, every sample assertion, declaration determinism included, and offline cache reuse. `smoke-prebuilt-linux-arm64` repeats the whole smoke on `ubuntu-24.04-arm`, which exercises the arm64 native. The macOS and windows natives ship without a CI execution job on purpose. They are upstream esbuild release binaries, lock-verified, and ts0.cjs itself is platform-neutral.
- **The `publish` job is the STOCK action**, `wow-look-at-my/buildhost/.github/actions/buildhost-publish@master`, with `artifact_name: prebuilt` and no inline publish scripting. If the action ever lacks something, fix it upstream in the buildhost repo. Never hand-roll a step here. It self-serves the run artifact. It runs a pre-publish guard that scans the run's jobs and the head commit's check runs, hence `actions: read` plus `checks: read`. The guard fails closed without both. It authenticates through GHA OIDC (`id-token: write`), and buildhost auto-provisions the projects, public because this repo is public. It maps files by naming convention. `ts0_cosmo_any` becomes project `ts0`, one artifact under the cosmo/any multi-platform alias: one stored body, resolvable under every `?os=..&arch=..` pair. `esbuild-<version>_<os>_<arch>[.exe]` becomes project `ts0/esbuild-<version>`. Each push creates a new release of BOTH projects. The natives' bytes are identical across re-publishes of one esbuild version, and ts0.cjs's version-less fetch URL always resolves the latest. `scripts/build-prebuilt.ts` owns the naming. A rename there is therefore a publish-layout change. EVERY branch publishes. buildhost treats the git branch as a first-class field, and the apex "latest" only ever resolves the default branch. A branch release therefore cannot hijack what stable consumers download. Gating the job on master instead left the only part of CI that talks to buildhost skipped on every PR. A change to it then passed CI without running once.
- **Org merge gate and job naming.** Merging into master needs a green `all-builds` commit status on the PR head SHA. An org app posts it automatically: required-builds-manager, which aggregates every build on the SHA. The gate needs no special CI job naming. Never name a job `all-builds`. The buildhost publish actions fail any run whose SHA carries a job by that name. The error says to rename it. Use a neutral name such as `aggregate` if a fan-in job is ever wanted.
