# Testing

Extracted verbatim from `CLAUDE.md`, where this had outgrown an index entry. See `CLAUDE.md`'s "Working on the code" section for the short version and the commands to run these locally.

Unit tests are every `src/**/*.test.ts`. One globbed CI step runs them all, `node --experimental-strip-types --test "src/**/*.test.ts"`, so a new test file needs no edit to the workflow:

- `src/runtime/fetch-interceptor.test.ts` evaluates the single-file fetch interceptor against a window/document shim and asserts it serves embedded assets for string, `URL`-object, and `Request` fetch inputs.
- `src/commands/typecheck-entry.test.ts` drives the real `runTypecheck` over temp projects. It pins the gate's file set: a type error in the configured entry fails the gate, whether or not the entry sits in a dot-directory.
- `src/commands/test-discovery.test.ts` drives the real CLI over a temp project that holds a nested ts0 project. It pins the recursion. A broken nested project fails the parent's `build` AND `test`. The parent builds and tests a clean one. `ts0 run` builds only its own project.

Everything else is a **behavioural suite** in `tests/*.dats`, run by [dats](https://github.com/wow-look-at-my/dats). CI builds `dist/ts0`, `npm link`s it, fetches the dats binary and runs the suites. Every test stages its project into its own directory. It then asserts what the build WROTE, through declarative `outputs.files` match and notMatch checks, and uses shell only for a property that spans files. A staged project gets the repo's `node_modules` symlinked in. That is the position it resolves `@types/node` and `preact` from when it is built in place.

Every file declares `network: false`, so a local run proves a build never needs a network. **CI runs `--no-sandbox` and therefore does not prove it.** The org's self-hosted runner denies unprivileged user namespaces, so bwrap cannot start and there is no docker fallback. Run the suites locally, with bwrap installed, to exercise the sandboxed contract.

- `tests/cli.dats` -- `ts0 init` scaffolds a project that `build`, `run` and `test` then handle end to end. `--config <path>` builds a named config from elsewhere in the tree, and rootDir stays the config file's own directory.
- `tests/gate.dats` -- the unskippable gate. A type error must make **every** path (`build`, `run`, `run --no-build`, `test`) exit non-zero and emit or execute nothing. That holds for the node target and the js (directory) target alike: no `.js` tree, and no partial `.d.ts`. The fixtures are shaped so a skipped check still looks fine. The error strips to valid JS and the test file registers no tests, so `--no-build` and `test` each exit 0 when the gate is bypassed. The suite then walks the explicit-`any` ban across every spelling: `x: any`, `as any`, `<any>`, `any[]`, `Promise<any>`, `type A = any`, and an `any` inside a `.d.ts`. It proves the look-alikes still build: identifiers, object keys, strings, comments and regexes that read "any". That is the guard that the ban stays a parse. Last, `exclude` limits the gate without changing the build, and a type error in an **HTML** entry fails the build. HTML entries were once exempt and reported success regardless.
- `tests/samples.dats` -- one test per sample. `basic`: build plus `ts0 test`. `html`: JS and CSS inlined into one document, `url()` rewritten to `data:`, inline-module bundling, and the fetch interceptor with no leftover `__ASSETS_JSON__`. The same test covers the CLI `--entry`/`--outfile` overrides. `html-jsx`: the automatic Preact runtime, no `React.createElement`, and a JSX tagline reading "any questions" that must survive. `js`: `ts0 test` runs first, because it EXECUTES `vec.test.ts` and so catches an import that bundles but that Node cannot resolve at run time. The build then mirrors the tree, dedupes shared code into a chunk rather than copying it, and applies the `.frag` text loader. It also emits the parallel `.d.ts` tree: `.ts`/`.tsx` specifiers preserved, no `.d.ts` for tests or chunks, no `.d.ts.map`, and byte-identical declarations across a rebuild. The same sample proves the `"declarations": false` opt-out. It also proves the `"bundleShared": false` inverse: a chunk with one shared body by default, then zero chunks with that body copied into each importer. `userscript`: the `==UserScript==` header byte-exact at the top, exactly once, and stable across a rebuild. Also an IIFE on the configured global, with no module statements and no shebang. `bookmarklet`: the `javascript:<file>` href percent-encoded and decoding back to the bundled program, and a real `javascript:void(0)` href untouched. `external-css`: the `with { type: "css" }` import emitted verbatim, the stylesheet text absent from every emitted file, and a neighbouring ordinary import still bundled. Its guardrail follows -- the same program WITHOUT `external` must fail the build and write nothing, because silent inlining defeats the feature.
- `tests/html-referenced.dats` -- the multi-file HTML target (`inlineAssets: false`). The shell plus one real bundle per reference under `assetPath`, with nothing inlined, the references rewritten, and the external stylesheet untouched. A **basename collision** fails the build with nothing written.
- `tests/node-target.dats` -- what a node-target build owes the machine that runs the output. `bundleDependencies: true` compiles an imported package in, proved by moving `node_modules` away before the artifact runs. The default leaves the `require("pkg")` call for the installed tree to answer. Then `ts0 test` runs in each module format. A `"type": "commonjs"` project keeps `__dirname`, `require` and extensionless imports. An ES module project keeps `import.meta.dirname` pointing at its own directory. And `require.main === module` inside a module under test FIRES, because one bundle is one module. The suite pins that, so it is learned from a test rather than from a mystifying CI failure.
- `tests/concurrency.dats` -- `ts0 test` runs a project's test files at the same time, on a wall clock rather than by inspecting an argv list. Two files each block for 1.5s, once under a `TS0_TEST_CONCURRENCY` of 1 and once under the default. The forced run doubles as the negative control: it can only cost both files while ts0 passes `--test-concurrency`, so dropping that flag turns the suite red. node defaults its runner to `availableParallelism() - 1`, which is 1 on a two-core CI runner and made every suite cost the sum of its files.
- `tests/action.dats` -- `action.yml` runs `test` then `build`, in that order, with no command input for a caller to point at `--help`. No `node` line interpolates an expression. The input set is exactly `working-directory`.

CI still builds the two HTML samples into the workspace after the suites. That step is not a test. It only produces the downloadable artifacts.

If you change CLI behavior, update the relevant `samples/*` and the matching `tests/*.dats` suite so the new behavior is covered.
